# Unrecoder — план разработки

Источник: `Unrecoder_Pitch_EN.pdf` (Nikita Doroshenko, 2026.10).

## 1. Суть игры (из питча)

- Ты радист-дешифровщик. Экспедиция из 10 человек идёт по горам через чекпоинты (CP1–CP4), собирает образцы, чинит маршрут/хижины/снаряжение.
- Каждая передача — шифр: блоки цифр и букв, **1 символ = 1 слово, 1 блок = 1 предложение**.
- Таблица кодов **меняется каждую передачу** — выучить коды нельзя; постоянно **правило построения таблиц**, его игрок постепенно осваивает.
- Только 1–2 символа за передачу имеют 2–3 значения. Именно они решают исход.
- Цикл: получить → расшифровать по таблице → выбрать прочтение → отдать приказ (Continue / Wait / Back to last CP / Hurry / Return to base) → результат виден в **следующей** передаче.
- Нет game over; люди могут пострадать или погибнуть. Хорошая расшифровка без потерь → Intuition Points, которые автозаполняют однозначные символы (неоднозначные — всегда сам).
- Шифр всегда решаем: правильное прочтение выводится из контекста (список экипажа, роли, состояние, прошлые сообщения) — как в примере с мостом (ремонтник ранен → «bridge broken», а не «repaired»).
- Сигнал ухудшается с глубиной, может улучшаться от локации/оборудования.
- PC (Steam), 3–4 часа, аудитория — любители головоломок.
- UI: стол с листами таблиц кодов, радио-экран, справа список экипажа, внизу карта.

## 2. Решение: сначала HTML-прототип, потом Unity

**Рекомендую HTML-прототип.** Главный риск проекта — не техника, а *дизайн*: работает ли загадка (честная, решаемая, с «щелчком» понимания). Это проверяется на тексте и таблицах, без графики. HTML даёт итерацию за минуты, прототип можно сразу дать друзьям по ссылке. Unity на этом этапе — лишние сборки и сцены.

Что переносить в Unity: **данные и логику**, не код. Поэтому с первого дня:
- вся логика (генерация таблиц, симуляция экспедиции, разбор приказов) — в изолированном модуле без привязки к DOM;
- контент (миссии, экипаж, фразы) — в JSON, который Unity прочитает как есть;
- логика на TypeScript → портируется в C# почти построчно.

## 3. Этапы

### Этап 0 — Дизайн-ядро (на бумаге, 2–4 дня) ← самое важное
Решить до кода (см. раздел 5):
1. Правило построения таблиц (как символы привязываются к словам, что даёт «выучиваемость»).
2. Как состояние мира (экипаж, роли, место) однозначно определяет верное прочтение неоднозначного символа.
3. Словарь: ~60–100 слов, грамматика предложения (кто / действие / объект / состояние).
4. Модель сообщения команды: где, что делает, состояние, что планирует.

### Этап 1 — HTML-прототип «вертикальный срез» (1–2 недели)
Стек: Vite + TypeScript, без фреймворков (чистый DOM/Canvas), тесты на логику (vitest).
- Один экран: радио-экран с шифром, таблица кодов, список экипажа, карта, выбор приказа.
- 1 цепочка из ~5–8 передач, написанная вручную, с 1–2 неоднозначными символами.
- Симуляция: прочтение → приказ → следующая передача (ветвление по правильности).
- Intuition Points и автозаполнение однозначных символов.
- Ранения/смерти членов экипажа влияют на последующие сообщения.
- **Критерий успеха:** 3–5 тестеров доходят до «щелчка» и до «я ошибся» без объяснений от тебя.

### Этап 2 — Расширение прототипа (1–2 недели)
- Генератор таблиц по найденному правилу (процедурно, с seed).
- Эффект сигнала: шум/пропуски в шифре, зависимость от глубины и оборудования.
- Полная карта (CP1–CP4 + база), 10 членов экипажа с ролями.
- Сквозная кампания на 15–25 передач → оценка, дотягивает ли до 3–4 часов.

### Этап 3 — Порт в Unity (2–3 недели)
- Проект Unity 6 LTS (URP 2D), uGUI или UI Toolkit.
- Порт логики в C# (`Unrecoder.Core` — чистые классы без MonoBehaviour, с NUnit-тестами, сверка с TS по тем же JSON/seed).
- Загрузка контента из JSON/ScriptableObjects.
- Сцена «стол»: рация, листы таблиц, список экипажа, карта.

### Этап 4 — Арт, звук, полировка (4+ недель)
- Эстетика экспедиционного лога/топографической карты (как в питче), аналоговые шумы рации — звук критичен.
- Сохранения, настройки, локализация (EN/RU/JA — тема «わ»).
- Steam: интеграция, достижения, страница магазина.

## 4. Структура репозитория

```
Unrecoder/
├─ docs/            # питч, план, дизайн-заметки
├─ prototype/       # HTML-прототип (Vite + TS)   — Этап 1–2
│   └─ src/core/    # чистая логика, без DOM
├─ content/         # JSON: словарь, экипаж, миссии (общий для прототипа и Unity)
└─ unity/           # Unity-проект                — Этап 3+
```

Unity-проект кладём в `unity/`, `.gitignore` с `Library/`, `Temp/`, `Logs/`, `UserSettings/` и т.д. уже подготовлен.

## 5. Открытые вопросы дизайна (решить на Этапе 0)

1. **Какое «правило построения таблиц»?** Примеры: первый символ всегда обозначает категорию (цифра = место/люди, буква = действие); порядок символов в таблице подчиняется алфавиту/частоте; символы из одного «семейства» — родственные слова. Правило должно быть открываемо и давать честную подсказку.
2. **Как гарантировать решаемость?** Для каждой неоднозначной передачи — формальная проверка, что ровно одно прочтение согласуется с состоянием мира (тест в коде: генератор не выпускает передачу без единственного решения).
3. **Что значит «ошибся»?** Правильность — по каждому неоднозначному символу или по всему предложению? Цена ошибки: ранение / задержка / смерть / потеря образцов?
4. **Роль приказа vs. прочтение:** одно и то же прочтение + разный приказ → разный результат? (Из примера: A + Wait ✓.) Нужна матрица «ситуация × приказ».
5. **Сигнал:** это шум в символах (часть пропала → угадывать по контексту) или только сложность? Влияет ли он на Intuition?
6. **Карта:** отмечает ли игрок позиции сам (механика) или это только визуализация?
7. **Смерть членов экипажа:** влияет ли на то, что команда *может* сделать (как у ремонтника → мост)? Это ядро логики вывода.

## 6. Риски

| Риск | Что делать |
|---|---|
| Загадка нечестная/слишком простая или сложная | Дизайн-ядро на бумаге + ранний плейтест на HTML |
| Контента на 3–4 часа слишком много писать вручную | Шаблоны сообщений + процедурная генерация таблиц; ручными делать только ключевые сюжетные передачи |
| Логика «верного прочтения» ломается при комбинации событий | Автотесты: симулятор прогоняет сотни случайных кампаний, проверяя решаемость |
| Порт TS→C# расходится | Общий JSON-контент + одинаковые тест-векторы по seed |
